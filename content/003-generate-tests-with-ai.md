# 用 AI 给旧代码补测试，不要让它乱写

## 开头

很多人试过让 AI 写测试，结果经常翻车：

- 编造不存在的函数
- 假设不存在的测试框架
- 只覆盖 happy path
- 测试看起来很多，但没测到风险点

问题不一定是 AI 不行，而是任务给得太粗。

这篇文章演示一种更稳的方式：先让 AI 做测试设计，再让它生成测试骨架。

## 不要一上来就说“帮我写测试”

更好的提示词应该要求 AI 先输出：

- Test Strategy
- Test Cases
- Missing Context
- Example Test Skeleton

也就是先问：

> 应该测什么？

再问：

> 代码怎么写？

## 测试生成工作流

推荐流程：

```text
代码/diff -> 测试策略 -> 测试用例表 -> 测试骨架 -> 人工补齐细节
```

其中 AI 最擅长的是前两步：发现边界条件和列测试点。

## 示例场景

假设有一个价格计算函数，需求包括：

- 支持优惠券
- 支持会员折扣
- 支持运费
- 金额不能为负

不要直接让 AI 写测试文件。

先让它列测试用例：

```markdown
| Case | Input/Setup | Expected Result | Why |
| --- | --- | --- | --- |
| 普通订单 | 无优惠券，无会员 | 返回商品金额 + 运费 | 基础路径 |
| 优惠券大于金额 | 优惠券金额超过商品金额 | 商品金额按 0 处理 | 防止负数 |
| 会员折扣和优惠券同时存在 | 两种优惠同时存在 | 按业务规则计算 | 组合风险 |
```

这个表格比直接生成代码更容易 Review。

## 适合写进团队规范的规则

让 AI 生成测试时，我会强制要求：

1. 先列测试点，再写代码。
2. 不确定测试框架时先给伪代码。
3. 明确哪些地方需要 mock。
4. 优先覆盖高风险路径，不追求数量。
5. 不编造业务规则。

对应模板在：

```text
templates/test-generation-prompt.md
```

## 可以自动化的地方

结合 Git diff，可以做一个工具：

```text
git diff -> AI 分析改动 -> 输出 Tests To Add
```

这不一定直接生成完整测试文件，但它可以在 PR Review 阶段提醒：

- 这个分支没有测试
- 这个边界条件缺失
- 这个错误分支没有覆盖
- 这个 API 兼容性风险需要回归测试

## 结论

AI 写测试的正确姿势不是“帮我补测试”。

更好的方式是：

> 让 AI 先帮你找测试风险，再让它生成可修改的测试骨架。

这样可控得多，也更适合真实项目。
