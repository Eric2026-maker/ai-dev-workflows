# Codex 插件推荐：Browser 插件，让 AI 真正打开页面做前端验收

很多人用 Codex 或其他 AI 编程工具做前端时，会停在这一步：

> 让 AI 写代码，然后看终端有没有报错。

但前端有一类问题，终端看不出来，代码也不一定一眼看出来：

- 移动端文字溢出
- 按钮在真实页面里不可点击
- 弹窗被遮挡
- loading 状态没有显示
- 表单提交后没有反馈
- 页面在浏览器里空白
- 某个元素被 fixed header 挡住

所以这一期我推荐一个很实用的 Codex 插件使用方式：

> 用 Browser 插件，让 Codex 打开本地页面，像 QA 一样检查真实渲染和交互。

## 为什么这个插件值得用

AI 写前端代码时，最大的问题不是不会写组件。

更大的问题是：

> 它没有真的看见页面。

只读代码时，AI 很容易漏掉视觉问题。

比如：

- CSS 看起来没问题，但移动端标题超出屏幕
- 表单逻辑写了，但按钮点了没有反馈
- 弹窗组件存在，但实际被遮罩层盖住
- 页面布局在 1440px 正常，390px 直接崩掉

Browser 插件补上的，就是“真实观察”这个环节。

## 推荐工作流

我建议把前端任务拆成这样：

```text
写代码 -> 启动本地服务 -> Browser 打开页面 -> 点击/截图/检查 -> 回到代码修复 -> 再次验证
```

这比单纯让 AI 写代码靠谱很多。

因为它形成了一个闭环：

```text
生成 -> 观察 -> 判断 -> 修复 -> 验证
```

## 一个实用 Prompt

你可以直接这样对 Codex 说：

```text
请使用 Browser 插件打开 http://localhost:3000。

检查：
1. 首页是否正常渲染
2. 移动端 390px 宽度下是否有文字溢出
3. 主要按钮是否可点击
4. 表单提交是否有反馈
5. 是否有明显遮挡、空白或错位

如果发现问题，请回到代码里修复，并再次用 Browser 验证。
```

这个 Prompt 的关键点是：

- 给明确 URL
- 给明确 viewport
- 给明确检查项
- 要求发现问题后修复
- 要求修复后再次验证

不要只说：

```text
帮我看看页面有没有问题。
```

这个太泛了。

## Browser 插件适合检查什么

我会优先让它检查这些东西：

### 1. 页面是否真的渲染

很多问题不用看代码，打开页面就知道：

- 白屏
- 首屏缺内容
- 图片没加载
- 样式没生效
- 页面高度异常

### 2. 移动端是否可用

短视频、独立站、管理后台移动适配，经常出问题。

重点看：

- 标题是否太大
- 按钮文字是否被截断
- 表格是否横向溢出
- 卡片是否挤在一起
- 弹窗是否超出屏幕

### 3. 关键交互是否能走通

比如：

- 搜索
- 筛选
- 登录
- 表单提交
- 打开弹窗
- 切换 tab
- 上传文件

AI 只看代码，可能觉得逻辑没问题。

但 Browser 能真的点一下。

### 4. 状态是否完整

前端最容易漏的是状态：

- loading
- empty
- error
- success
- disabled
- hover / focus

这些状态不一定会在默认页面里出现，需要明确要求 Codex 去触发或模拟。

## 输出应该长什么样

我希望 Codex 每次 Browser QA 后输出这样的结构：

```markdown
## Browser QA Result

- URL:
- Viewport:
- Status:

## Findings

1.
2.
3.

## Fixes

- File:
- Change:

## Verification

- Desktop:
- Mobile:
```

这样你能清楚知道：

- 它看了哪个页面
- 用了哪个尺寸
- 发现了什么问题
- 改了哪些文件
- 是否二次验证通过

## 使用时要注意什么

Browser 插件很实用，但不要把它当成人类设计师。

它更适合做：

- 明确检查
- 明确点击
- 明确截图
- 明确回归验证

不适合只说：

```text
帮我把页面变高级。
```

这种需求太主观，反馈会漂。

更好的说法是：

```text
请检查这个页面在 390px 宽度下是否有文字溢出、按钮遮挡和横向滚动。
```

## 我的建议

如果你用 Codex 做前端，我建议把 Browser QA 作为固定步骤。

每次前端任务结束前，都加一句：

```text
请用 Browser 打开页面，分别检查桌面端和移动端。发现问题后修复，并再次验证。
```

这句话能减少很多“代码看起来完成了，但页面其实不能用”的问题。

## 总结

这一期推荐的不是一个炫技插件，而是一个很实用的工程闭环：

> 让 AI 不只写代码，还要打开页面，看页面，点页面，再修页面。

Browser 插件的价值就在这里。
